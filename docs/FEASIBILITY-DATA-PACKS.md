# 数据扩展可行性：食材库 / 奶茶经典 / 地区日常菜

调研日期 2026-11-02。结论先行，后面是依据。**未改任何代码或数据。**

---

## 结论

**可行，但顺序要改。**

1. **食材库扩库是最该先做的**，也是唯一"缺了就真没兜底"的东西——用户说对了。抽查 49 项常见食材，**49 项全缺**。
2. **数据更新应该脱离 APK 版本，做成无感自动下载**：可行，因为写入层已经是 `REPLACE`（upsert）语义，差的是一个 manifest + 下载校验 + 版本表，约 3–4 天。数据只有几十 KB，**全量下载、不做增量**。
3. **地区不做八大菜系，做"饮食圈层 + 日常品类"**：衡阳这种地市级粒度，收粉/小炒这类日常高频；功夫菜（雪花鱼淖）不做。
4. **奶茶/连锁经典值得做**，60 个 SKU 约 10–15 小时，数值只能估值，现有界面已经能正确标注。

## 二、前置工程：数据必须能脱离 APK 版本更新

现状 `SeedImporter.ensureSeeded()`：

```kotlin
if (dao.count() > 0) return   // 有数据就什么都不做
```

后果：**已安装用户升级 APK 后，食物库不会变**。所以加多少数据都到不了老用户手里。

这一条的具体方案（无感下载、校验、事务写入、版本表）见**第六节**，约 3–4 天。它是所有数据扩展的地基，建议最先做。

## 三、三个方向的可行性

### A. 食材库扩库（建议优先）

**目标**：207 → 350~400 条，覆盖常见蔬菜/肉禽/水产/菌菇/豆制品/谷物半成品/乳蛋/调味/油/水果。

**每条的成本**（照现有 207 条的标准）：

| 工作 | 内容 |
|---|---|
| 数值 | 能量 + 蛋白 + 脂肪 + 碳水 + 钠（现有 207 条 100% 有钠） |
| 份量 | 2–3 个中式单位（一根/一把/一碗/一勺），现有库平均只有 1 个，扩库时顺手补 |
| 别名 | 1–2 个（方言、简称、常见错写） |
| 复核 | `source` 标注 + `verified` |

单条 6–8 分钟 → **100 条约 12–15 小时**；到 400 条约 **25–30 小时**（含整理与自检）。

**代码成本：接近零**（纯 CSV 行 + 上面的增量导入）。

**主要风险是数据来源与许可**，见第四节。

### B. 奶茶 / 连锁经典（无营养成分表）

**范围**：60 个 SKU 左右（蜜雪、喜茶、奈雪、茶百道、古茗、瑞幸、霸王茶姬、星巴克中国的招牌款）。

**哪些有官方数据**（决定每条是 `brand_official` 还是 `estimate`）：

| 品牌 | 官方公示情况 |
|---|---|
| 喜茶 | 2023.10 起小程序公开 40+ 款配方及每杯热量/蛋白/脂肪/碳水 → 可直接引用 |
| 霸王茶姬 | 热量计算器 + GI + 分级，按容量/甜度/温度 → 粒度最细，最值得收录 |
| 瑞幸 | 官网产品页有每杯热量 + 咖啡因，注明杯型/冰/糖 |
| 奈雪 | 小程序标"热量估算值"；瓶装茶有每 100ml 营养表 |
| 茶百道 | 2023.8 送检 4 款并公布（大杯/全糖/去冰） |
| 蜜雪、古茗、星巴克中国 | **无官方每杯表**（星巴克仅美国官网有）→ 只能估值 |

| 项 | 说明 |
|---|---|
| 每条工作 | 1 条食物 + 2–4 个规格（中杯/大杯/超大杯）+ 1 个别名 ≈ 10–15 分钟 → **10–15 小时** |
| 现有能力 | 界面已支持 ml 单位、杯型份量、`verified=0` 标"市售典型值"，**不需要改代码** |
| 合规 | GB 28050 对"现制现售"食品**豁免强制营养标示**，所以没官方表是合规现状；品牌名属**指示性使用**，可用，但：不用官方 logo、`notes` 标"非官方估算"、注明规格与日期 |
| 维护策略 | 只收"上市 ≥3 年的招牌款"，新品不维护——写进 schema 文档，否则以后被追着加新品 |

### C. 地区日常菜（不是菜系）

**这一项需要改数据模型，但改动很小**：

| 需要 | 说明 |
|---|---|
| `region` 字段 | 食物表加 `region`（`CORE` / `湘·衡阳` / `湘·长沙` / `川·成都` …），默认 `CORE`，迁移 v4 |
| ID 分配 | `F001` 递增且**永不复用**（日记快照引用）→ 地区食物用独立前缀（`HN001`、`HN002`），不续 F 号 |
| 菜品数值 | lint 禁止手填 DISH，必须由配方推导 → 每道菜 = 1 配方头 + 约 3 个食材 + 2–3 个份量 + 1–2 个别名 |
| 单道菜成本 | 粉/小炒这类结构简单，**10–15 分钟**（比功夫菜省一半） |
| 试点成本 | 衡阳 20–30 道（粉/小炒/卤味）≈ **6–10 小时** |
| 代码成本 | `region` 字段 + 地区筛选 + 偏好开关 ≈ **1–2 天** |

**明确不做**：八大菜系全覆盖、功夫菜（雪花鱼淖/文思豆腐）、新品维护。详见第五节。

**安装形态：数据全量在包里，用偏好开关而不是"下载安装"**——数据几十 KB，下载安装 UI 是纯成本。

## 四、数据来源与许可（已调研，结论明确）

| 来源 | 许可 | 能不能用 |
|---|---|---|
| **USDA FoodData Central** | 美国政府作品 **CC0** | ✅ 可直接用、可商用、可再分发。但中式食材覆盖弱，只适合补基础蔬菜/肉类 |
| **《中国食物成分表》第6版** | 版权属中国疾控中心营养与健康所，无免费全量授权 | ⚠️ **数值本身不受著作权保护**（2006 年判例），但"选择+分类+编码"的**编排**是汇编作品，整表照搬判赔 5.6 万元。**引用单条数值、自行重编**可行 → 我们现在的做法在安全侧，但不能整表搬 |
| **Open Food Facts** | **ODbL**（传染性） | ❌ 不适合：衍生数据库也要 ODbL，会污染我们的闭源种子数据。且中国现制饮品几乎空白 |
| **公开菜谱数据集** | 下厨房语料标 MIT 但源站再分发许可不明；ChineseFoodNet 仅限研究 | ❌ 不能用 → 配方必须自写 |
| **品牌官方营养公示** | 事实数据 | ✅ 可用并附 `source_url`（喜茶/瑞幸/霸王茶姬/奈雪/茶百道有，蜜雪/古茗/星巴克中国无） |

**菜谱本身**：配方、用量、步骤不受著作权保护，受保护的是图文表达 → 我们写"食材+克数+烹饪方式"的结构化配方没有版权问题。

**结论**：食材数值（FCT 单条引用 + USDA 补基础）可行；菜品必须自己编配方；奶茶按品牌公示引用、无公示的估值并标 `verified=0`。

## 五、地区颗粒度：不按菜系，按"饮食圈层 + 日常品类"

八大菜系是**出版物的分类法**，不是吃饭的分类法。真实需求是"我这儿早餐吃什么、中午小炒吃什么"。

### 两个标签替代一个菜系字段

| 标签 | 取值 | 作用 |
|---|---|---|
| `region` | `CORE`（通用）/ `湘·衡阳` / `湘·长沙` / `川·成都` / `粤·广州` / `东北·哈尔滨` … | 到**地市/饮食圈层**，不是省也不是菜系 |
| `category` | 早餐粉面 / 小炒 / 家常菜 / 汤 / 夜宵 / 主食 / 卤味 / 下饭菜 … | 按**吃的场景**分类，现有 category 直接扩枚举 |

### 衡阳的例子（这正是该覆盖的粒度）

| 食物 | 配方拆解 | 现有引擎能否算 |
|---|---|---|
| 衡阳卤粉 | 米粉 + 卤水 + 码子（肉末/牛肉） | ✅ 3 个食材，正好等于现有配方平均值 3.6 |
| 肉末粉 | 米粉 + 肉末 + 高汤 | ✅ |
| 鱼头粉 | 米粉 + 鱼头 + 汤 | ✅ |
| 辣椒炒肉 | 五花肉 + 青椒 + 油 | ✅ |
| 衡阳小炒 | 五花肉/猪肝 + 配菜 + 油 | ✅ |
| 剁椒鱼头 | 鱼头 + 剁椒 + 油 | ✅ |

**粉类是这个方向的关键**：粉 = 米粉 + 码子 + 汤底，天然符合"食材 + 克数 + 烹饪方式"的推导模型，不需要新引擎。

### 明确不做

- **功夫菜**（雪花鱼淖、文思豆腐这类）：配方复杂、点单率低、数据成本高
- **菜系全覆盖**：不做"八大菜系各 30 道"这种工程
- **新品维护**：只收长期在售的日常款

### "用户选择性安装"简化为偏好开关

数据全量在包里（几十 KB 级），**不需要下载安装 UI**：

- 默认：`CORE` + 用户所在地区（可手动改）
- 选了地区 → 该地区食物在搜索结果里优先、在"查找"里多一个地区筛选项
- 未选 → 只有通用库，行为和现在一样

## 六、无感数据更新：与 APK 版本解耦，可行

**结论：可行，而且比"跟版本更新"更简单**，因为数据库写入层已经是 upsert 语义。

### 为什么现在不行、差什么

```kotlin
// 现状：有数据就再也不导入
if (dao.count() > 0) return
```

但三个种子 DAO 都是 `@Insert(onConflict = REPLACE)`：

```kotlin
@Insert(onConflict = OnConflictStrategy.REPLACE) suspend fun insertFoods(...)
```

→ **同一份全量数据再写一次，就等于 upsert**：新 id 插入、老 id 覆盖、用户自建（`CUSTOM`/扫标签的 `L…`）不受影响。日记存的是快照，改食物数值不会篡改历史记录。

### 最小架构

```
启动后延迟几秒 → GET manifest.json（最多 1 次/天）
  { "dataVersion": 12, "url": "...", "sha256": "...", "bytes": 183000, "minAppVersion": "0.9.0" }
        │ 版本比本地新
        ▼
  下载到 cacheDir/data/data-v12.zip
        │ 校验 SHA-256（不一致就丢弃，保留旧数据）
        ▼
  解析 + 校验（kcal 0–900、kind 枚举、name 长度、行数）
        │ 全部合法才进下一步；任一行不合法 → 整包丢弃
        ▼
  单事务写入（foods → servings → aliases）
        │ 失败回滚，旧数据完好
        ▼
  记录 appliedDataVersion → 静默完成
```

### 关键取舍

| 决策 | 原因 |
|---|---|
| **全量下载，不做增量 diff** | 数据几十 KB（现在 63 KB，扩到 350 食材约 150 KB，压缩后 30–50 KB），做 diff 是纯增加复杂度 |
| **整包要么全过、要么全丢** | 半包写入会让库处于"部分新部分旧"的不一致状态 |
| **失败静默** | 数据更新失败不该打扰用户，也不该影响记账；只在「我的」里显示上次更新时间 |
| **manifest 带 `minAppVersion`** | 防止老版本 App 读到它不认识的新字段 |
| **dataVersion 单调递增** | 远端更旧直接忽略，避免回滚数据 |
| **宿主用 GitHub Releases** | 复用现有 APK 下载的镜像链 + SHA-256 机制，不需要新后端；数据包作为 release asset 发 |

### 安全边界（必须说清）

- 数据**不执行代码**，最坏情况是被塞进错误数值
- 校验 SHA-256 + 字段范围（kcal ≤ 900、营养素 ≥ 0、枚举合法、行数上限）
- 仓库被投毒 → 只能污染数值，不能执行任意代码；界面仍有 `verified` 标注
- 不做签名校验（要做需引入密钥管理，当前收益不值）

### 工程量

| 项 | 估算 |
|---|---|
| manifest 拉取 + 版本比较 + 下载 + 校验（复用 `ApkInstaller` 的镜像/重试/摘要代码） | 1 天 |
| CSV 解析复用 `SeedImporter` + 单事务写入 + `seed_meta` 表 + v4 迁移 | 1 天 |
| 校验器（范围/枚举/行数）+ 测试（幂等、坏包、断网、降级、并发） | 1 天 |
| 「我的 → 数据更新」状态行（上次更新时间 + 手动检查） | 0.5 天 |

**约 3–4 天**，比"随 APK 更新"只多 1 天，但换来数据可以独立发版。

## 七、建议路线

| 阶段 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| **P0** | 无感数据通道（manifest + 下载校验 + 事务写入 + 版本表） | 3–4 天 | 数据可独立发版，不再绑定 APK |
| **P1a** | 食材补 P0 缺口 22 项（调味料/油/主食半成品/草鱼黑鱼/常见蔬菜） | 约 3 小时 | 先堵"做菜算不准"的硬缺口 |
| **P1b** | 食材补 P1 缺口 71 项 | 8–10 小时 | 常用食材基本齐全（约 300 条） |
| **P1c** | 食材补 P2 缺口 60 项 | 7–8 小时 | 收尾，接近"齐全" |
| **P2** | 奶茶/连锁经典 60 SKU（有公示的引官方，其余估值） | 10–15 小时 | 高频且现在完全空白 |
| **P3** | 地区标签 + 衡阳试点（粉/小炒 20–30 道） | 6–10 小时数据 + 1–2 天代码 | 验证"地市级"粒度是否有人用 |

P1 每批验收：`python tools/check_coverage.py --strict` 通过（P0 无缺口）+ `seed_lint.py` 0 error + `derive_dish.py` 跑完菜品数值无漂移。

**为什么食材优先于菜品**：菜品是"食材 + 克数 + 烹饪方式"的推导结果，缺一个食材，含它的所有菜都算不准；用户能自己用现有食材拼出菜品（组合菜品功能），却**没法凭空补出一个食材的准确营养值**。食材齐全后，复杂菜谱算不动时的兜底就是"用食材自己拼"。

P3 试点选衡阳而不是川菜：**粉 + 小炒的配方结构简单、日常频次高**，正好落在现有推导引擎的能力范围内。

## 八、决策点（需要你定）

1. **食材清单够不够**：`coverage_targets.csv` 目前 178 项（P0 22 / P1 71 / P2 60）。要不要再加（比如更多地方蔬菜、内脏、干货），还是先按这 178 项补齐？
2. **先动哪一批**：建议 P1a（22 项硬缺口，约 3 小时）先落，还是先把 P0 数据通道做完再批量补？
3. **地区先做衡阳试点**（粉/小炒 20–30 道）可以吗？还是先要别的城市？
4. **奶茶只收"招牌 + 上市 ≥3 年"**、有官方公示的引官方其余标估值 —— 这个口径确认吗？
5. **数据包发在哪个 release 通道**：跟 App 版本同一个 GitHub Release，还是单独一个 `data` release（tag 如 `data-v12`）？建议后者，互不干扰。

## 九、如果决定推进，第一批具体动作

1. P0：`seed_meta` 表 + 无感数据通道 + 校验器 + 测试（3–4 天）
2. P1 按整类缺口分批补食材：调味料 → 内脏/淡水鱼 → 菌菇干货 → 主食半成品 → 油/乳品，每批跑 `seed_lint` 0 error
3. 每批补完跑 `derive_dish.py`，确认菜品数值未漂移
4. P2 奶茶 60 SKU（`PACKAGED` + `AS_SOLD` + ml + 杯型份量）
5. P3 加 `region` 字段 + 衡阳 20–30 道（粉/小炒）+ 地区筛选 UI
